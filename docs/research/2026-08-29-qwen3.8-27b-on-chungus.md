# Running Qwen3.8-27B on chungus with llama.cpp

- **Date:** 2026-08-29
- **Host:** `chungus` (RTX 4090 24 GiB VRAM, 64 GB system RAM)
- **Scope:** Research only. No production Nix configuration was changed.

## Executive recommendation

The newly released model is exactly **`Qwen/Qwen3.8-27B`**, not Qwen3.5-27B. Qwen published it on 2026-08-05, and the repository describes a dense 27B causal language model with a vision encoder, 64 language-model layers, and 262,144 tokens of native context. The implementation architecture remains named `qwen3_5`/`qwen35` in Transformers and GGUF metadata; that implementation name does not make the product model Qwen3.5. [Qwen model repository/API](https://huggingface.co/api/models/Qwen/Qwen3.8-27B) [Qwen model card](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/README.md) [Qwen config](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/config.json)

For `chungus`, start with Unsloth's **UD-Q4_K_M** GGUF (15.33 GiB) at **196,608 tokens**, `q4_0` K/V, Flash Attention, one server slot, and llama.cpp's automatic GPU fit. This is the best balance of quantization quality, long usable context, and GPU residency. The model plus 196K q4 KV is about 18.70 GiB before the approximately 0.86 GiB vision projector, recurrent state, CUDA work buffers, and other allocations. Omit the projector for text/coding use. The GGUF file sizes are first-party repository metadata from the quantizer; the memory totals are derived below. [Unsloth GGUF repository/API](https://huggingface.co/api/models/unsloth/Qwen3.8-27B-GGUF?blobs=true) [llama-server flags](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/tools/server/README.md#common-params)

For the **full native 262,144-token window**, retain UD-Q4_K_M and q4 K/V, set `-ngl auto --fit on`, and reserve at least 2 GiB of VRAM with `--fit-target 2048`. llama.cpp can leave initial layers and their cache in system RAM if everything does not fit. If automatic fitting is unstable or still OOMs, the deterministic fallback is `-ngl all --no-kv-offload`: weights stay on the GPU while the 4.5 GiB KV cache and recurrent state stay in system RAM. That fallback has a substantial and context-growing PCIe performance penalty, but 64 GB RAM has ample capacity. [`-ngl`, `--fit`, and `--no-kv-offload` documentation](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/tools/server/README.md#common-params) [llama.cpp hybrid CPU/GPU goal](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/README.md#description)

## Model identity and architecture

Qwen's exact public identifier is `Qwen/Qwen3.8-27B`. Hugging Face reports creation on 2026-08-05, 27,781,427,952 BF16 parameters, model type `qwen3_5`, and architecture `Qwen3_5ForConditionalGeneration`. The product/model name and implementation architecture should therefore be kept distinct. [Hugging Face model API](https://huggingface.co/api/models/Qwen/Qwen3.8-27B?blobs=true) [Qwen config](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/config.json)

The language model is dense, not MoE. Its relevant dimensions are:

| Property | Value |
|---|---:|
| Language-model parameters | 27B advertised; 27,781,427,952 BF16 parameters in repository metadata |
| Hidden width | 5,120 |
| Layers | 64 |
| Pattern | 16 repetitions of 3 Gated DeltaNet layers plus 1 full-attention layer |
| Full-attention layers | 16 |
| Query heads | 24 |
| KV heads | 4 (GQA ratio 6:1) |
| Attention head width | 256 |
| Linear-attention heads | 16 QK, 48 V, width 128 |
| FFN width | 17,408 |
| Vocabulary/padded embedding rows | 248,320 |
| Vision encoder | 27 layers, width 1,152; separate GGUF projector available |

These values come directly from Qwen's model card and `config.json`; `full_attention_interval: 4` and the explicit layer list confirm that only every fourth layer has token-growing KV state. [Qwen model card, Model Overview](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/README.md#model-overview) [Qwen config](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/config.json)

llama.cpp recognizes this as GGUF architecture `qwen35`. Its Qwen35 loader marks layers recurrent unless every fourth layer is full attention, then uses a hybrid memory object: a normal token-growing KV cache for full-attention layers and fixed-size F32 recurrent state for Gated DeltaNet layers. [Qwen35 loader](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/src/models/qwen35.cpp#L4-L35) [Hybrid-memory selection](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/src/llama-model.cpp#L2424-L2541)

## Context support

The native context is **262,144 tokens** (`max_position_embeddings: 262144`). Qwen states that the model is extensible to **1,000,000 tokens**, and specifically recommends a RoPE scaling method such as YaRN only when total input plus output exceeds 262,144. Native 262K therefore needs no RoPE override. [Qwen model card](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/README.md#model-overview) [Qwen best practices](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/README.md#best-practices) [Qwen config](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/config.json)

`llama-server -c N` allocates the prompt context; `0` loads the model default. `--parallel N` controls server slots. For one maximum-length coding/agent session, explicitly use `--parallel 1`, otherwise slot behavior and concurrent requests can divide or compete for the context pool. [llama-server common and server-specific parameters](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/tools/server/README.md#common-params)

The current `chungus` lock pins llama.cpp commit `7e4c0a96880dae4fc4268ad441f8a6446bd5460a` from 2026-08-14. That revision already has `-ngl auto`, `--fit`, `--fit-target`, quantized KV types, Qwen35 hybrid memory, and `reasoning_effort` support. Updating llama.cpp before deployment is still prudent because Qwen3.8 is new and fixes continue landing rapidly. [Pinned llama.cpp commit](https://github.com/ggml-org/llama.cpp/commit/7e4c0a96880dae4fc4268ad441f8a6446bd5460a) [Pinned server README](https://github.com/ggml-org/llama.cpp/blob/7e4c0a96880dae4fc4268ad441f8a6446bd5460a/tools/server/README.md)

## KV and recurrent-state memory

### Exact attention KV calculation

Only 16 full-attention layers grow KV with context. Each token in each such layer stores:

```text
K elements = 4 KV heads * 256 dimensions = 1,024
V elements = 4 KV heads * 256 dimensions = 1,024
total      = 2,048 elements per layer per token
```

The dimensions and 16 full-attention layers come directly from Qwen's model card/config. llama.cpp allocates K and V tensors as `[n_embd_{k,v}_gqa, kv_size, streams]`, filtered to attention layers for Qwen35. [Qwen model card](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/README.md#model-overview) [llama.cpp KV allocation](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/src/llama-kv-cache.cpp#L157-L240) [Qwen35 attention filter](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/src/llama-model.cpp#L2466-L2472)

For F16, two bytes per element gives exactly `2,048 * 16 * 2 = 65,536 bytes`, or **64 KiB/token**. For q4_0, ggml stores 32 values in an 18-byte block (2-byte scale plus 16 packed bytes), or 0.5625 bytes/value, giving `2,048 * 16 * 18/32 = 18,432 bytes`, or **18 KiB/token**. Q8_0 stores 32 values in 34 bytes and therefore costs **34 KiB/token**. [ggml q4_0 block definition](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/ggml/src/ggml-common.h#L194-L199) [ggml q8_0 block definition](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/ggml/src/ggml-common.h#L233-L238)

| Context | q4_0 K+V | q8_0 K+V | F16 K+V |
|---:|---:|---:|---:|
| 32,768 | 0.563 GiB | 1.063 GiB | 2.000 GiB |
| 65,536 | 1.125 GiB | 2.125 GiB | 4.000 GiB |
| 131,072 | 2.250 GiB | 4.250 GiB | 8.000 GiB |
| **196,608** | **3.375 GiB** | **6.375 GiB** | **12.000 GiB** |
| **262,144** | **4.500 GiB** | **8.500 GiB** | **16.000 GiB** |
| 1,000,000 | 17.166 GiB | 32.425 GiB | 61.035 GiB |

This is why q4 K/V is essential on 24 GiB VRAM. At native context it saves 11.5 GiB versus F16. Quantizing KV can reduce long-context quality because keys and values are repeatedly consumed by attention; q4 is the capacity-first choice, while q8/F16 are quality-first choices that are not realistic at 196K-262K with full GPU residency. llama.cpp permits `q4_0`, `q8_0`, and F16 for both cache types and defaults to F16. [llama-server cache type documentation](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/tools/server/README.md#common-params)

### Fixed recurrent state

The other 48 layers use Gated DeltaNet recurrent state rather than a token-growing KV cache. llama.cpp keeps this state in F32 and allocates it per recurrent layer and server sequence, not per context token. The Qwen configuration gives state width 128, V inner width `48 * 128 = 6,144`, QK groups 16, and convolution width 4. From llama.cpp's formulas, one sequence needs roughly 144 MiB of matrix state plus 5.625 MiB of convolution state across 48 layers, around **150 MiB total**, independent of whether context is 32K or 262K. [Qwen config](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/config.json) [llama.cpp recurrent-state formulas](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/src/llama-hparams.cpp#L183-L233) [F32 hybrid-state selection](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/src/llama-model.cpp#L2524-L2541)

## How CPU/GPU offload uses both memory pools

`-ngl` is not a binary all-GPU switch. llama.cpp always keeps the input layer on CPU, then assigns a suffix of repeating layers and optionally the output layer to GPU. Layers before that suffix remain on CPU. `-ngl auto` leaves the count unset so `--fit` can choose what fits; `-ngl all` requests every offloadable layer. [Layer placement source](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/src/llama-model.cpp#L1390-L1492) [`-ngl` and fit documentation](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/tools/server/README.md#common-params)

With default KV offload enabled, each layer's KV or recurrent state follows that layer's assigned device. Therefore partial layer offload naturally uses both system RAM and VRAM for weights and cache. This is preferable to forcing the entire KV cache to CPU because GPU-resident attention layers can read their cache locally. [KV device assignment](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/src/llama-kv-cache.cpp#L208-L240) [Recurrent-state device assignment](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/src/llama-memory-recurrent.cpp#L77-L125)

`--no-kv-offload` disables cache/state GPU offload and places all of it in host memory even when weights are GPU-resident. It is the cleanest way to free 3.375-4.5 GiB of VRAM for 196K-262K context, but full-attention layers then repeatedly access host cache across PCIe. Expect decode speed to worsen as the attended context grows; this is a bandwidth consequence, not a capacity failure. [KV offload flag](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/tools/server/README.md#common-params) [KV CPU/GPU allocation source](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/src/llama-kv-cache.cpp#L208-L240)

The default model load mode is mmap when supported. CPU-resident tensors are file-backed and become resident through the OS page cache; `--load-mode mlock` can force them into RAM but reduces memory available to the rest of the system. Keep `--load-mode mmap`/default for this 64 GB machine unless paging is observed. [llama-server load modes](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/tools/server/README.md#common-params) [Model loader mmap behavior](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/src/llama-model-loader.cpp#L318-L382)

## Concrete llama-server profiles

The commands below use the existing llama-swap convention `${PORT}` conceptually; in Nix, retain the existing escaped `\${PORT}` form. They are command recommendations, not production-file edits.

### Recommended balance: 196K, automatic partial offload if needed

```bash
llama-server \
  --port "${PORT}" \
  -m /var/lib/llama-swap/models/qwen3.8/Qwen3.8-27B-UD-Q4_K_M.gguf \
  -c 196608 \
  --parallel 1 \
  -ngl auto \
  --fit on \
  --fit-target 1536 \
  --flash-attn on \
  --cache-type-k q4_0 \
  --cache-type-v q4_0 \
  -b 512 \
  --ubatch-size 512 \
  --load-mode mmap \
  --temp 1.0 \
  --top-p 0.95 \
  --top-k 20 \
  --min-p 0.0 \
  --reasoning on \
  --reasoning-effort xhigh \
  --reasoning-format deepseek
```

Why these choices:

- 196K q4 KV is exactly 3.375 GiB. Combined with the 15.33 GiB file, there is materially more GPU headroom than at 262K. The fit estimator can lower the GPU layer count instead of lowering the explicitly set context because it adjusts unset arguments; `-ngl auto` is intentionally unset while `-c` is fixed. [`--fit` semantics](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/tools/server/README.md#common-params)
- Flash Attention is explicitly supported as `on/off/auto`; quantized V cache should remain paired with Flash Attention for the intended compact, non-transposed V-cache path. [Flash Attention and cache flags](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/tools/server/README.md#common-params) [KV V-layout source](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/src/llama-kv-cache.cpp#L109-L112)
- `-b 512 --ubatch-size 512` is conservative for a 24 GiB card. Current llama.cpp defaults are logical batch 2048 and physical batch 512, but larger prompt batches need more temporary VRAM. [Batch flag definitions](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/tools/server/README.md#common-params)
- Qwen's official thinking-mode recommendation is temperature 1.0, top-p 0.95, top-k 20, min-p 0, presence penalty 0, repetition penalty 1. The existing 0.6 coding temperature was a Qwen3.5-era local choice, not Qwen3.8's published recommendation. [Qwen best practices](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/README.md#best-practices)
- Thinking is on by default. Qwen supports `xhigh`, `medium`, and `low` reasoning effort; llama.cpp's reasoning flags pass this to the embedded template and can expose thought separately as `reasoning_content`. [Qwen model card, flexible thinking](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/README.md#qwen38-highlights) [llama-server reasoning flags](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/tools/server/README.md#server-specific-params)

For vision, add:

```text
--mmproj /var/lib/llama-swap/models/qwen3.8/mmproj-F16.gguf
```

Expect the projector to reduce available context/layer headroom by roughly 0.86 GiB. [Unsloth file metadata](https://huggingface.co/api/models/unsloth/Qwen3.8-27B-GGUF?blobs=true)

### Native maximum: 262,144 tokens

```bash
llama-server \
  --port "${PORT}" \
  -m /var/lib/llama-swap/models/qwen3.8/Qwen3.8-27B-UD-Q4_K_M.gguf \
  -c 262144 \
  --parallel 1 \
  -ngl auto \
  --fit on \
  --fit-target 2048 \
  --flash-attn on \
  --cache-type-k q4_0 \
  --cache-type-v q4_0 \
  -b 512 \
  --ubatch-size 512 \
  --load-mode mmap \
  --temp 1.0 \
  --top-p 0.95 \
  --top-k 20 \
  --min-p 0.0 \
  --reasoning on \
  --reasoning-effort xhigh \
  --reasoning-format deepseek
```

This allocates exactly 4.5 GiB of q4 KV before overhead. With text-only weights, raw weights plus KV are about 19.83 GiB. A 24 GiB card has only about 4.17 GiB left for recurrent state, CUDA context, graph/work buffers, output tensors, display use, and allocator margin, so full offload is plausible but not guaranteed. `--fit-target 2048` deliberately leaves a 2 GiB target margin and allows CPU layers rather than silently shrinking the fixed 262K context. [`--fit-target` semantics](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/tools/server/README.md#common-params)

If the fit estimator still OOMs or chooses an unreliable layout, use this deterministic host-cache variant:

```text
-ngl all --no-kv-offload
```

Remove `-ngl auto --fit on --fit-target 2048` when adding it. This leaves approximately 15.33 GiB of quantized model weights on GPU (plus runtime overhead), while moving the 4.5 GiB KV cache and approximately 150 MiB recurrent state to system RAM. It maximizes native context capacity and uses both memory pools, but is expected to be substantially slower at long context because attention cache traffic crosses PCIe. [`--no-kv-offload` and `-ngl all`](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/tools/server/README.md#common-params)

### Experimental 1M extension: capacity fits, usability is doubtful

Qwen says 1M is an extension target, not the native window, and recommends YaRN beyond 262,144. llama.cpp documents `--rope-scaling yarn`, `--rope-scale N`, and `--yarn-orig-ctx N`; a factor of 4 extends 262,144 to 1,048,576 positions. [Qwen best practices](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/README.md#best-practices) [llama.cpp RoPE/YaRN flags](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/tools/server/README.md#common-params)

An experimental text-only command is the native-max command changed to:

```text
-c 1000000
--rope-scaling yarn
--rope-scale 4
--yarn-orig-ctx 262144
-ngl all
--no-kv-offload
```

At 1,000,000 tokens q4 KV alone is about 17.17 GiB. Together with the 15.33 GiB GGUF and runtime allocations, it is within 64 GB host capacity, but capacity is not usability: prefill is enormous, 16 layers still perform full attention, CPU-hosted KV crosses PCIe, prompt ingestion will take a long time, and quality under this exact llama.cpp YaRN setup is not established by Qwen. Treat 1M as an experiment, not a service profile. The recommended practical ceiling on this host is the native 262K window. [Qwen model card context claim](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/README.md#model-overview) [llama.cpp hybrid inference scope](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/README.md#description)

## Expected limits and tradeoffs

1. **Context allocation is not the same as context speed.** Q4 KV makes 262K fit, but full-attention decode still reads an ever-growing cache in 16 layers. Long-context token generation will slow as the active context grows even though the other 48 layers are recurrent. The 16/48 split is architectural. [Qwen model card](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/README.md#model-overview)
2. **Partial weight offload costs latency on every token.** llama.cpp assigns early repeating layers to CPU and a suffix to GPU. A CPU/GPU boundary therefore introduces CPU compute and transfer each forward pass. Prefer a smaller quant with more GPU layers over Q6 with many CPU layers when responsiveness matters. [Layer placement source](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/src/llama-model.cpp#L1467-L1492)
3. **Host KV is a last-resort capacity mode.** It preserves GPU weight compute but makes attention consume host memory over PCIe. Use automatic mixed layer/cache placement first, then `--no-kv-offload` only for native-max/1M experiments. [KV placement source](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/src/llama-kv-cache.cpp#L208-L240)
4. **One slot is important.** More sequences require more recurrent-state rows and can partition or compete for the context pool. Use `--parallel 1` for a single maximum-context agent. [Server slot and parallel flags](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/tools/server/README.md#server-specific-params) [Recurrent allocation per sequence](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/src/llama-memory-recurrent.cpp#L20-L39)
5. **Vision consumes both model memory and tokens.** The projector costs about 0.86 GiB, and images/videos add visual tokens to the same context. Keep separate text and vision llama-swap entries if maximum coding context matters. [Unsloth projector files](https://huggingface.co/api/models/unsloth/Qwen3.8-27B-GGUF?blobs=true) [llama-server multimodal flags](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/tools/server/README.md#server-specific-params)
6. **Avoid MTP during initial capacity testing.** The separate Q4_0 MTP file is 1.28 GiB before its runtime allocations. Establish stable context and measure baseline first. [Unsloth MTP file metadata](https://huggingface.co/api/models/unsloth/Qwen3.8-27B-GGUF?blobs=true)
7. **Use current llama.cpp and test the exact CUDA revision.** Qwen recommends latest framework versions, and current llama.cpp issue traffic shows that Qwen3.8 paths are still receiving fixes. Do not infer that an issue on Blackwell or Qwen3.8-Flash-Next necessarily applies to Ada/Qwen3.8-27B, but do treat the release as young. [Qwen serving note](https://huggingface.co/Qwen/Qwen3.8-27B/blob/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/README.md#serving-qwen38) [llama.cpp Qwen3.8 issue search](https://github.com/ggml-org/llama.cpp/issues?q=Qwen3.8)

## Validation procedure before changing Nix

Run the recommended command manually against a temporary port, then inspect llama.cpp's startup memory report. It logs model buffers, per-device KV buffers, recurrent-state buffers, and offloaded layer count from the allocation paths cited above. [KV allocation logging](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/src/llama-kv-cache.cpp#L242-L268) [Recurrent-state logging](https://github.com/ggml-org/llama.cpp/blob/c9ca51c1f6b18427cde490c7c7eba11d87a96b2d/src/llama-memory-recurrent.cpp#L117-L137)

Record:

```bash
nvidia-smi
curl -s http://127.0.0.1:${PORT}/health
curl -s http://127.0.0.1:${PORT}/slots | jq
```

Test at least 32K, 128K, 196K, and near-262K prompt lengths; record prompt-processing tokens/s, generation tokens/s, peak VRAM, host RSS, and whether llama.cpp reduced GPU layers. Only after that should the selected profile be translated into `hosts/chungus/services/llama-swap.nix`.

## Bottom line

- Exact model: **Qwen3.8-27B**, GGUF architecture label `qwen35`.
- Architecture: dense 27B VLM, 64 layers, 48 recurrent Gated DeltaNet plus 16 full-attention GQA layers.
- Native context: **262,144**; 1M is a YaRN extension target.
- Recommended quant: **UD-Q4_K_M, 15.33 GiB**.
- Recommended operating point: **196,608 tokens**, q4 K/V, `-ngl auto --fit on`, one slot, no projector for text.
- Native maximum: **262,144 tokens**, q4 K/V, automatic partial offload; fall back to all GPU weights plus host KV with `--no-kv-offload`.
- Exact q4 KV: **18 KiB/token**, 3.375 GiB at 196K, 4.5 GiB at 262K, 17.17 GiB at 1M.
- Practical judgment: 262K should be achievable with 24 GiB VRAM plus 64 GB RAM; 1M may fit in aggregate memory but is unlikely to be pleasant or production-worthy on a single RTX 4090.
