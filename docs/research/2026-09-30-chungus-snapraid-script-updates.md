# Chungus SnapRAID script update status

- **Date:** 2026-09-30
- **Scope:** Research only; no Nix configuration or deployed packages changed.

## Recommendation

**Do not update either pin as a proposed fix for the kernel fault.** The runner is already at its upstream head and latest release; the shell wrapper's fork is only one copyright-only commit behind its own head. Keep the Snapper-compatible fork (or carry its one-line fix onto upstream) until the actual `snapper get-config` output is tested. More urgently, fix/test the runner's *interrupted-sync + empty-diff* path before relying on unattended cleanup: the existing runner can skip the sync that would establish a successfully synced snapshot, then invoke cleanup. This is a workflow/data-recovery risk, not evidence of a kernel-memory bug. ## Compatibility and failure modes

- The fork's [`828ee50` change](https://github.com/D34DC3N73R/snapraid-btrfs/commit/828ee50da210dffdaabf422692af89177317396c) recognizes the Unicode `│` in `snapper get-config`'s `SUBVOLUME` table as well as ASCII `|`; pinned [`ea9a1cf` consolidates that sed expression](https://github.com/D34DC3N73R/snapraid-btrfs/commit/ea9a1cfbfbe1cefcae9c038e1a4962d4bc2de843). The local comment says Snapper 0.11.1; fork commit says 0.11.0. This is a parsing fix, not a general guarantee of compatibility with every future Snapper format. If parsing fails, autodetection may silently use the live data filesystem instead of snapshots; verify `snapraid-btrfs --verbose ls` sees `/data` and the `data` Snapper config before switching. [Upstream setup and fallback behavior](https://github.com/automorphism88/snapraid-btrfs/blob/6492a45ad55c389c0301075dcc8bc8784ef3e274/README.md#L27-L77) [Chungus storage layout](../../hosts/chungus/services/storage.nix).
- The pinned runner calls `diff` and counts `add/remove/move/update`; if the sum is zero it **does not call `sync`**, but still proceeds to `pool`, `cleanup`, and optional `scrub`. SnapRAID's diff reflects file changes, not proof that a previous parity-writing sync completed. The shell wrapper only marks snapshots `synced` after `snapraid sync` returns successfully, and its cleanup retains the last marked-synced snapshot; the wrapper explicitly provides `resume` for interrupted syncs. After an interrupted sync, **do not treat `diff=0` as successful sync completion**: inspect snapshots/parity state, resume against the original snapshots or complete a deliberate sync, and defer cleanup until completion is established. Do not simply delete snapshots or force cleanup-all. [Runner branch](https://github.com/fmoledina/snapraid-btrfs-runner/blob/afb83c67c61fdf3769aab95dba6385184066e119/snapraid-btrfs-runner.py#L308-L368) [Wrapper sync marking](https://github.com/D34DC3N73R/snapraid-btrfs/blob/ea9a1cfbfbe1cefcae9c038e1a4962d4bc2de843/snapraid-btrfs#L1330-L1364) [Wrapper cleanup](https://github.com/D34DC3N73R/snapraid-btrfs/blob/ea9a1cfbfbe1cefcae9c038e1a4962d4bc2de843/snapraid-btrfs#L409-L440) [Upstream README](https://github.com/automorphism88/snapraid-btrfs/blob/6492a45ad55c389c0301075dcc8bc8784ef3e274/README.md#L143-L153).
- **False copy detection is a SnapRAID heuristic, not fixed by these script revisions.** SnapRAID's [`-N, --force-nocopy`](https://www.snapraid.it/manual#options) disables matching by name/size/timestamp when it gives false positives, at the cost of not reusing copy/hash information. The wrapper passes arguments *after* `sync` to SnapRAID, but the runner currently hardcodes its own SnapRAID arguments and has no config field for `-N`; manual `snapraid-btrfs sync -N` is a diagnostic option, not an unattended runner fix. Separately, the wrapper's [known UUID limitation on snapshot paths](https://github.com/automorphism88/snapraid-btrfs/blob/6492a45ad55c389c0301075dcc8bc8784ef3e274/README.md#L341-L349) prevents inode-based move detection; don't conflate that with a proven cause of a specific copy warning. [Argument forwarding documentation](https://github.com/automorphism88/snapraid-btrfs/blob/6492a45ad55c389c0301075dcc8bc8784ef3e274/README.md#L15-L24) [Runner argument builder](https://github.com/fmoledina/snapraid-btrfs-runner/blob/afb83c67c61fdf3769aab95dba6385184066e119/snapraid-btrfs-runner.py#L34-L65).
- The local runner has `cleanup = true`, `pool = false`, `scrub.enabled = false`, a 40-delete threshold, explicit executable paths and `/etc/snapraid.conf`; changing to a different runner/fork must preserve these semantics and Nix shebang/PATH wrapping. The wrapper recommends separate content-file subvolumes, and Chungus has one at `/mnt/data-snapraid-content`; parity is on XFS at `/mnt/snapraid-parity1`. [Local runner config](../../hosts/chungus/pkgs/snapraid-btrfs-runner.nix) [Local storage config](../../hosts/chungus/services/storage.nix) [Upstream setup](https://github.com/automorphism88/snapraid-btrfs/blob/6492a45ad55c389c0301075dcc8bc8784ef3e274/README.md#L56-L71).

## Kernel-fault assessment

The complete oops supplied for kernel **7.2.6** places the fault in `xas_create` → `xas_store` → `__filemap_add_folio` → `iomap_file_buffered_write` → `xfs_file_buffered_write` during SnapRAID's `pwrite64`. That identifies the page-cache/XFS parity-write path where the thread died, not a shell/Python instruction. On this host SnapRAID writes the [XFS parity/content location](../../hosts/chungus/services/storage.nix), so sync can **trigger** that path or expose an underlying kernel, filesystem, hardware, or memory problem; these script pins do not change XFS kernel code. The trace alone cannot distinguish a kernel defect from memory/hardware corruption. Test kernel/filesystem/hardware separately before blaming or updating scripts. [Linux kernel bug-hunting guidance on complete decoded traces](https://docs.kernel.org/admin-guide/bug-hunting.html) [Chungus parity and service paths](../../hosts/chungus/services/storage.nix).
